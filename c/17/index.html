17.2.2 Debug 和 Release

模式 特点 用途
Debug 保留调试信息，优化少 开发、调试
Release 开启优化，程序更快更小 发布

调试时使用 Debug 模式。

有时程序在 Debug 下正常，在 Release 下出错。这通常说明代码里有未定义行为或隐藏 bug。

17.3.1 常见错误类型回顾

类型 发生阶段 例子
编译错误 编译 少分号、括号不匹配
链接错误 链接 函数只有声明没有定义
运行时错误 运行 空指针、除零、越界
逻辑错误 运行 计算错误、条件写反
内存错误 运行 泄漏、悬空指针、重复释放
未定义行为 运行 有符号溢出、越界访问

调试的第一步是判断错误属于哪一类。

17.3.6 assert 与防御性编程

assert 用于检查“不应该发生”的情况。

如果条件为假，程序会终止并输出错误位置。

注意：

  • assert 适合调试阶段；
  • 定义 NDEBUG 后，assert 会被禁用；
  • 不要用 assert 处理用户输入错误；
  • 用户输入错误应该用普通的 if 判断。

防御性编程：

核心思想：

不要假设输入一定合法，不要假设指针一定有效。

17.3.7 重构与代码评审

重构：

在不改变程序外部行为的前提下，改进代码内部结构。

重构前：

  • 先有测试；
  • 小步修改；
  • 每改一步就运行一次；
  • 不要一边重构一边加功能。

代码评审清单：

  • 命名是否清楚？
  • 函数是否单一职责？
  • 有没有重复代码？
  • 有没有魔法数字？
  • 注释是否解释“为什么”？
  • 是否检查了返回值？
  • 是否检查了空指针？
  • 是否有内存泄漏？
  • 是否有越界风险？
  • 是否有未定义行为？
  • 错误提示是否清楚？
  • 一周后还能看懂吗？

17.3.8 本章代码规范：先让程序正确，再让程序优雅

这一章最重要的规范是：

先让程序正确，再让程序优雅。

顺序应该是：

不要为了“好看”牺牲正确性。

其他建议：

  • 先写测试用例，再改代码；
  • 使用 Debug 模式调试；
  • 使用 -Wall -Wextra 编译；
  • 使用 gdb、Valgrind、Sanitizer 等工具；
  • 记录并复现 bug；
  • 修复后做回归测试；
  • 重构时保持行为不变；
  • 提交代码前做一次自测和代码评审。

17.6 常见错误

错误 1：不调试，直接乱改代码

正确做法是先定位，再修改。

错误 2：只看最后一条错误

编译错误应该从第一条开始看，后面的错误可能只是连锁反应。

错误 3：忽略警告

警告往往提示潜在 bug，不要忽略。

错误 4：只测正常情况

只输入正确数据，不测试：

  • 空数据；
  • 边界值；
  • 非法输入；
  • 删除头节点；
  • 删除尾节点。

很多 bug 都藏在这些情况里。

错误 5：修复后不做回归测试

修好一个 bug，可能把另一个功能改坏。

修复后要重新运行之前的测试。

错误 6：用 assert 处理用户输入

用户输入错误应该用 if 判断并提示。

错误 7：调试信息一直留在正式版本里

调试完后要删除或通过条件编译关闭。

错误 8：重构时同时加新功能

重构和新功能混在一起，出错后很难判断是哪一部分导致的。

错误 9：内存检查工具报告了问题却忽略

Valgrind 或 Sanitizer 报告的问题通常都很重要，不要因为“程序还能跑”就忽略。

错误 10：发布前不做最终检查

发布前应该对照检查清单，确认关键路径都测过。

17.7 总结与自测

一句话总结

调试是定位问题的过程，测试是验证正确性的过程；先用 Debug 模式和工具找到问题，再用测试和回归保证修复没有引入新问题；最后通过重构和代码评审让程序更清晰。核心原则是：先让程序正确，再让程序优雅。
