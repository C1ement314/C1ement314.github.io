前面七章主要在学“怎么写才能让程序跑起来”。这一章要停下来做一件更重要的事：

怎么写，才能让代码更像给人看的，而不是只给机器执行的？

代码规范不是花架子。它决定了你一个星期后还能不能看懂自己的代码，也决定了别人愿不愿意和你一起做项目。

代码规范的目的不是“让代码看起来漂亮”，而是：

  • 减少出错；
  • 减少重复；
  • 方便自己以后回来看；
  • 方便别人读懂；
  • 方便团队协作；
  • 方便测试和维护。

一句话：

代码首先是写给人看的，其次才是给机器执行的。

当然，规范不是越复杂越好。初学阶段先做到“清楚、一致、不别扭”就够了。

8.2.3 注释规范

注释不是越多越好，关键是写到点子上。

注释解释“为什么”

不好的注释：

这个注释只是复述代码，没有增加信息。

更好的注释：

这个注释解释了业务规则。

注释要及时更新

如果代码改了，注释没改，错误注释比没有注释更危险。

这种注释会误导读者。

函数注释

对稍微复杂的函数，可以在函数上方说明：

  • 这个函数做什么；
  • 参数是什么意思；
  • 返回值是什么；
  • 有没有副作用。

  • 文件名；
  • 行号；
  • 列号；
  • 错误级别（error 或 warning）；
  • 错误说明。

  • 错误：return 前面少了分号。

阅读错误信息的顺序

  1. 从第一条错误开始看

    • 后面的错误可能只是第一条错误引起的连锁反应。

  2. 看文件名和行号

    • 定位到代码附近。

  3. 不要只盯着报错那一行

    • 错误可能出在上一行或上一个语句。

  4. 看清 error 还是 warning

    • error 通常必须修；
    • warning 也不能随便忽略。

  5. 只看关键信息

    • 编译器输出可能很长，先看第一个 error。

常见错误关键词

关键词 大概意思
expected ';' 可能少了分号
undeclared identifier 使用了未声明的名字
implicit declaration 函数没有声明就被使用
conflicting types 类型声明冲突
unused variable 变量声明了但没使用
format '%d' expects 格式说明符和参数类型不匹配
control reaches end of non-void function 非 void 函数可能没有返回值

遇到错误时，不要急着改一大堆代码。先看第一条错误，改掉，再重新编译。

8.3 进阶篇：再懂原理

基础篇讲的是“怎么写更顺眼”。进阶篇要讲“怎样让代码长期可维护”。

8.3.1 可读性与可维护性

可读性是指：

别人能不能比较容易地看懂你的代码。

可维护性是指：

以后修改、扩展、修复代码时，成本高不高。

可读性差会直接影响可维护性。

常见降低可读性的做法：

  • 变量名无意义；
  • 函数太长；
  • 嵌套太深；
  • 重复代码太多；
  • 魔法数字太多；
  • 注释和代码不一致；
  • 格式混乱。

提高可读性的方向：

  • 名字清楚；
  • 函数短小；
  • 一个函数只做一件事；
  • 减少重复；
  • 用常量代替魔法数字；
  • 保持格式一致；
  • 注释解释为什么。

有一个重要原则：

不要只考虑“现在我能不能写出来”，还要考虑“以后我还能不能改”。

8.3.2 函数拆分

函数太长，是初学者常见的问题。

例如：

这个函数虽然能写，但职责太多。

更好的方式是拆成：

  • read_student_count
  • read_total_score
  • calculate_average
  • calculate_grade
  • print_result

每个函数只做一件事。

什么时候应该考虑拆分函数？

  • 函数超过一屏；
  • 函数里有多个“阶段”；
  • 函数里嵌套太深；
  • 函数名很难起，因为做了太多事；
  • 一段代码在多个地方重复出现；
  • 你需要写很多注释才能说明某一段在做什么。

拆分函数的好处：

  • 更容易阅读；
  • 更容易测试；
  • 更容易复用；
  • 更容易定位问题。

当然，也不要走极端。一个只有一两行、含义非常清楚的功能，不一定非要拆成函数。

8.3.3 重构

重构是指：

在不改变程序外部行为的前提下，改进代码的内部结构。

简单说就是：功能不变，代码变好。

常见重构方法：

  1. 重命名

    • 把 a、b 改成有意义的名字。

  2. 提取函数

    • 把一段重复或复杂的代码抽成函数。

  3. 替换魔法数字

    • 用 const 常量代替无意义的数字。

  4. 减少嵌套

    • 用提前返回、拆分条件等方式减少层级。

  5. 消除重复

    • 把重复代码合并到一个函数里。

  6. 简化条件

    • 把复杂条件拆成多个简单条件，或者抽成函数。

重构的原则：

  • 小步进行；
  • 每次只改一点；
  • 每改一次就重新编译、运行；
  • 不要一边重构一边加新功能；
  • 最好有测试或可验证的输入输出。

8.3.4 防御性编程

防御性编程是指：

不要假设输入一定合法，不要假设函数调用一定成功。

常见做法：

  1. 检查输入范围；
  2. 检查除数是否为 0；
  3. 检查数组下标是否越界；
  4. 检查函数返回值；
  5. 检查文件是否成功打开；
  6. 检查内存申请是否成功；
  7. 对 switch 加 default；
  8. 错误时给出清楚提示并安全退出。

8.3.5 如何阅读别人的代码

阅读代码是一项重要能力。

面对一个陌生项目，可以按下面的顺序：

  1. 先看项目说明

    • README、注释、文档。

  2. 找到程序入口

    • 通常是 main 函数。

  3. 从 main 开始，顺着调用关系往下看

    • 先看主流程，不要一头扎进细节。

  4. 看函数名和函数签名

    • 先猜函数做什么，再进去看实现。

  5. 使用调试器

    • 打断点、单步执行、看调用栈、看变量变化。

  6. 运行程序

    • 观察输入输出，建立直观印象。

  7. 修改一小处，再运行

    • 通过实验理解代码行为。

  8. 做笔记

    • 画出模块关系、数据流、函数调用关系。

  9. 不要一开始就追求全部看懂

    • 先理解主流程，再逐步深入细节。

阅读代码的核心是：

先看结构，再看细节；先跑起来，再改一处看结果。

8.3.6 代码审查清单

每次完成一个功能后，可以对照下面的清单检查：

  • 变量名、函数名是否有意义？
  • 函数是否只做一件事？
  • 有没有重复代码？
  • 有没有魔法数字？
  • 注释是否解释“为什么”，并且和代码一致？
  • 缩进、空格、花括号是否一致？
  • 是否检查了输入和返回值？
  • 是否有除数为 0 的风险？
  • 数组或缓冲区是否可能越界？
  • 循环边界是否正确？
  • switch 是否处理了 default？
  • 编译是否有 warning？
  • 错误信息是否对用户友好？
  • 代码是否容易测试？
  • 一周后自己还能看懂吗？

这份清单不需要每次都全部背诵。初学阶段，能养成其中一半的习惯，代码质量就会明显提高。

8.5 本章代码规范提示

  • 变量名用有意义的名词，函数名用动词，常量名全大写。
  • 保持统一的 snake_case 风格。
  • 使用 4 个空格缩进，花括号成对，一行一条语句。
  • 运算符两边加空格，逗号后面加空格。
  • 注释解释“为什么”，并且和代码保持一致。
  • 用 const 代替魔法数字。
  • 函数保持单一职责，不要过长。
  • 复杂功能拆成小函数，再由主函数组合。
  • 重构时小步进行，不要改变程序行为。
  • 检查输入、返回值、除零、越界等情况。
  • 养成阅读编译错误和警告的习惯。
  • 阅读别人的代码时，先看结构，再看细节。
  • 规范是为了更清楚，而不是为了形式主义。

错误 4：注释和代码不一致

注释说平均分，代码算的是总分。错误注释比没有注释更误导人。

错误 5：格式混乱

虽然能编译，但很难读。应该加上缩进、空格和换行。

错误 6：嵌套太深

嵌套太深会增加理解成本。可以用提前返回、拆分函数、整理条件来减少嵌套。

错误 7：忽略编译警告

警告不是摆设。它可能提示你写错了变量名，或者有代码没有真正使用。

错误 8：重构时改变了程序行为

重构的前提是：

不改变程序的对外行为。

如果一边重构一边改功能，出了问题就很难判断是重构引入的，还是新功能引入的。

错误 9：重复代码不提取

如果某段代码反复出现，或者结构非常相似，可以考虑提取成函数。

8.7 总结与自测

一句话总结

代码规范的核心是让人看懂、让程序好改；命名要清楚，格式要一致，注释解释为什么，常量代替魔法数字，函数保持单一职责，重构时小步前进，读写代码都要先看结构再看细节。

  1. 因为代码会被自己、同事和未来的自己阅读、修改和维护，清楚比“炫技”更重要。
  2. 变量名用有意义的名词；函数名用动词；常量名通常全大写加下划线；整体保持 snake_case 风格。
  3. 应该优先解释“为什么”，而不是简单复述代码做了什么。
  4. 魔法数字是代码中含义不明确的数字；可以用 const 常量给它起名字。
  5. 函数太长、嵌套太深、职责太多、重复代码多、很难起名、需要很多注释说明时，都可以考虑拆分。
  6. 重构是在不改变程序外部行为的前提下，改进代码内部结构。
  7. 小步进行，每改一点就重新编译、运行，确保行为不变。
  8. 检查输入范围、返回值、除零、越界、文件打开失败、内存申请失败等情况，并给出清楚提示。
  9. 先看项目说明，再找 main，顺着调用关系看主流程，然后看函数签名、调试运行、修改一小处、做笔记，不要一上来就陷进细节。
  10. 因为警告往往提示潜在 bug、类型不匹配、未使用变量或未定义行为，忽略警告可能让问题以后才爆发。
  11. 开放题，按自己的实际情况回答即可。
  12. 开放题，能说出具体一点的理由即可。
